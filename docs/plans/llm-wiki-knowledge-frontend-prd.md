# llm_wiki 知识库前端页面 PRD

## 1. 指导口径

本阶段前端只面向一种知识库：`llm_wiki` 文档知识库。页面可以参考 yuxi 的知识库体验，但不能照搬它的多知识库类型、RAG 评估、评估基准、Agent 扩展等能力。

`llm_wiki` 知识库的核心不是普通 RAG 列表，而是一个由上传文件驱动、通过两步式 LLM 摄取生成 wiki 结构、同时沉淀图谱和可追溯检索结果的企业知识空间。

必须保留的核心方法论：

- 三层架构：Raw Sources -> Wiki -> Schema/Rules。
- 三个核心操作：Ingest、Query、Lint。
- `index.md` 作为内容目录和 LLM 导航入口。
- `log.md` 作为可解析的时序操作记录。
- `overview.md` 作为全局摘要，摄取后自动更新。
- `purpose.md` 表达知识库目标、关键问题、研究范围和演进方向。
- `schema.md` 表达 wiki 结构规则、页面类型和写作约束。
- `[[wikilink]]` 用于 wiki 页面交叉引用。
- 每个 wiki 页面必须有 YAML frontmatter，至少包含类型、标题、来源和更新时间。
- 人类策展，LLM 维护：用户决定资料、审核和方向，LLM 负责持续生成、整理、关联和维护。

## 2. 数据与权限约束

每个知识库必须绑定：

- `kb_id`：数据库真实 ID，也是文件存储目录名。
- `tenant_id/company_id`：公司租户 ID。
- `created_by`：创建者用户 ID。
- `visibility`：`company` 或 `creator_only`。
- `type`：固定为 `llm_wiki`，前端不提供类型切换。

数据与权限必须采用组合隔离：

- 所有知识库数据查询都必须同时带上 `tenant_id/company_id` 和 `kb_id`。
- 所有文件、wiki 页面、图谱节点、图谱边、embedding chunk、review item、ingest job、chat session 都必须绑定 `tenant_id/company_id` 与 `kb_id`。
- 文件唯一性使用组合键：`tenant_id/company_id + kb_id + root(raw/wiki) + relative_path`。
- 任意接口不得只凭 `kb_id` 或 `relative_path` 读写数据。
- `kb_id` 是数据库真实 ID 和文件目录名，但权限判断必须仍然回到 `tenant_id/company_id + visibility + created_by`。

文件存储约束：

- 知识库物理根目录固定为 `database/{kb_id}/`。
- 用户上传的所有源文件进入 `database/{kb_id}/raw/`。
- LLM Wiki 生成的所有 wiki 文件进入 `database/{kb_id}/wiki/`。
- 从目录结构上必须一眼看出这是 `llm_wiki` 思想：`raw` 是用户材料，`wiki` 是模型基于材料生成的知识结构。
- 数据库只保存结构化元数据与相对路径，不保存本地绝对路径。
- 文件记录以 `relative_path` 作为目录树、源追溯、wiki 生成和检索引用的统一定位字段。
- 删除知识库时，删除对应数据库记录与 `database/{kb_id}/` 下的文件对象。
- 前端界面不展示 `database/{kb_id}` 这个物理前缀，只展示 `raw/` 与 `wiki/` 下的业务目录结构。
- 支持上传文件夹，并保留用户上传时的相对目录结构。
- 同一路径重复上传时采用同名覆盖规则：新文件替换旧文件内容，数据库中保持同一个相对路径的唯一记录，并触发对应文件的重新摄取、wiki 增量更新和图谱/检索索引刷新。
- 文件夹本身也是一等元数据：即使文件夹不作为可检索文档，也必须保存目录节点、父子关系、完整相对路径和上传批次。
- 每个源文件必须保存 `folder_context`：由相对路径、父级目录名、同级文件、上传批次和用户选择的目标目录生成。
- `folder_context` 必须进入两步式摄取的第一步分析提示，作为 LLM 判断文档分类、主题归属、wiki 页面路径和实体上下文的输入。
- wiki 页面 frontmatter 必须保留来源文件的 `relative_path` 和 `folder_context` 摘要，确保目录语义进入 `llm_wiki` 生成结果。
- `wiki/` 目录至少包含：
  - `index.md`：内容目录和 LLM 导航入口。
  - `log.md`：摄取、删除、审核、研究等操作日志。
  - `overview.md`：全局摘要。
  - `purpose.md`：知识库目标和研究范围。
  - `schema.md`：页面类型、命名、frontmatter、wikilink 规则。
  - `sources/`：源文件摘要页。
  - `entities/`：实体页。
  - `concepts/`：概念页。
  - `queries/`：有价值问答和研究结论归档。
  - `synthesis/`：跨来源综合分析。
  - `comparisons/`：对比分析。

访问规则：

- `visibility=company`：公司所有成员登录后可见。
- `visibility=creator_only`：仅创建者可见；平台管理员/公司管理员后续可另行定义管理权限。
- 当前用户进入列表页时，只看到自己有权访问的知识库。

## 3. 页面信息架构

### 3.1 全局应用框架

采用 yuxi 类似的左侧窄导航；引导页不展示导航，其他业务页常驻导航：

- `/` 是系统引导页，不直接展示知识库列表。
- 引导页简单介绍系统定位：企业级 `llm_wiki` 知识库、两步式摄取、raw/wiki 结构、图谱和可追溯检索。
- 引导页主按钮为 `开始体验`，点击进入 `/database`。
- `/database` 是知识库列表页，展示知识库卡片和 `新建知识库` 按钮。
- `/database/{kb_id}` 是知识库详情页，展示该知识库的文件、wiki、图谱、检索和审核能力。
- 详情页返回按钮固定返回 `/database`。
- 顶部显示组织头像或系统 logo。
- 侧边栏上方固定两个入口：
  - 知识库：进入 `/database`。
  - 扩展管理：作为二阶段能力入口预留，不混入当前 `llm_wiki` 摄取主链路。
- 侧边栏下方固定运维和账号入口：
  - 任务中心：承载持久化摄取队列、失败重试、取消和进度总览。
  - 公司设置：仅平台管理员和公司管理员可见，维护租户、LDAP、模型池和默认模型。
  - 个人头像：打开个人菜单。
- 个人中心弹层包含：
  - 当前用户名、角色、公司。
  - 文档中心。
  - 退出登录。
- `退出登录` 必须在引导页、知识库列表页和知识库详情页都可用；进入 `/database` 或 `/database/{kb_id}` 后不能出现无法退出的状态。
- 退出后清理本地 token 和会话状态，并跳转到登录页。

不出现：

- 智能体入口。
- Dashboard。
- RAG 评估。
- 评估基准。

### 3.2 知识库列表页

目标：登录后第一眼看到自己可访问的 `llm_wiki` 知识库，并能新建知识库。

页面结构：

- 页面标题：`知识库`。
- 顶部切换：
  - `文档知识库`
  - `知识图谱`
- 右上角主按钮：`新建知识库`。
- 卡片列表：
  - 知识库图标。
  - 名称。
  - 文件数。
  - 创建时间或更新时间。
  - 描述。
  - 标签：`LLM Wiki`、文本嵌入模型、可见性。

新建知识库弹窗字段：

- 名称，必填。
- 描述，可选。
- 可见性：
  - 全公司可见。
  - 仅创建者可见。
- 模型选择：
  - 默认 LLM。
  - 文本嵌入模型。
  - 视觉模型，后续用于多模态图片摄取。
- 摄取默认策略：
  - 固定为 `llm_wiki`。
  - 展示但不允许切换：两步式摄取、wiki 生成、图谱关联、混合检索、Lint、异步审核。

创建成功后：

- 创建数据库记录。
- 初始化 `database/{kb_id}/` 文件根目录。
- 初始化 `raw/` 与 `wiki/` 目录。
- 初始化 `wiki/index.md`、`wiki/log.md`、`wiki/overview.md`、`wiki/purpose.md`、`wiki/schema.md`。
- 跳转到知识库详情页。

### 3.3 知识库详情页

目标：同屏管理文件、wiki 结构、图谱和召回/问答。

整体布局参考 yuxi：

- 左侧：知识库信息 + 文件/结构目录。
- 右侧：知识图谱、检索测试、知识导图或问答召回。
- 中间可拖拽调整宽度。

顶部信息卡：

- 返回按钮。
- 知识库名称。
- 描述。
- 标签：`LLM Wiki`、文本嵌入模型、视觉模型、可见性。
- 操作：
  - 复制知识库 ID。
  - 编辑名称/描述/可见性/模型。
  - 删除知识库。

左侧目录区需要有三个视角：

- `文件`：面向上传管理的源文件目录树，数据来自 `raw/`。
- `Raw`：原始材料结构，按 `database/{kb_id}/raw/` 下的相对路径组织，但界面只显示 `raw/` 内部目录。
- `Wiki`：LLM 生成的 wiki 页面结构，对应 `database/{kb_id}/wiki/`，界面只显示 `wiki/` 内部目录，包含 index、overview、规则页、主题页等。

文件目录能力：

- 上传文件。
- 上传文件夹并保留相对路径。
- 新建文件夹。
- 搜索文件名。
- 排序。
- 状态过滤。
- 刷新。
- 多选。
- 删除。
- 重新摄取。
- 查看摄取状态。
- 手动重扫 `raw/`。
- 自动监听 `raw/` 变化，检测新增、覆盖、删除，并同步触发摄取或级联清理。
- 上传文件夹后，界面必须展示原始文件夹树，而不是把文件拍平成列表。
- 同名覆盖只在同一个组合键内生效，不跨知识库、不跨公司、不跨 `raw/wiki` 根目录。
- 上传前前端必须根据目标存储路径检查是否存在同名文件。
- 若同一 `raw/relative_path` 已存在，必须弹出覆盖确认对话框，展示将被覆盖的相对路径、原文件更新时间和新文件名。
- 用户确认后才允许覆盖上传；取消则跳过该文件，不创建重复记录。
- 文件夹批量上传时，如存在多个冲突，必须展示冲突列表，并支持全部覆盖、全部跳过或逐项处理。

文件状态至少包括：

- 已上传。
- 队列中。
- 解析中。
- 生成 wiki 中。
- 构建图谱中。
- 生成 embedding 中。
- 等待审核。
- 已完成。
- 失败。
- 已取消。

点击文件时：

- 打开文件详情。
- 展示文件相对路径、大小、状态、错误、摄取日志。
- 展示文件夹上下文：父级目录、同级文件摘要、上传批次。
- 支持跳转到源文件预览。
- 支持查看关联 wiki 页面、引用实体、生成的 frontmatter。
- 如果文件包含图片抽取结果，展示图片说明和灯箱预览入口。

删除文件时：

- 删除对应 raw 文件。
- 删除或更新源摘要页。
- 从共享实体/概念页的 `sources[]` 中移除该来源。
- 清理 `index.md` 中的引用。
- 清理死 `[[wikilink]]`。
- 刷新图谱、embedding 和检索索引。

### 3.4 右侧知识图谱页签

目标：展示当前知识库的 4-Signal 图谱与 Louvain 社区结果。

能力：

- 默认加载当前知识库全局图谱摘要。
- 支持实体搜索。
- 支持刷新。
- 支持设置：
  - 最大节点数。
  - 搜索深度。
  - 是否按社区着色。
  - 是否显示边标签。
  - 类型着色或社区着色切换。
- 展示节点数、边数、社区数。
- 点击节点显示详情：
  - 实体名称。
  - 类型。
  - 摘要。
  - 来源文件 relative_path。
  - 相关 wiki 页面。
- 点击边显示详情：
  - 关系说明。
  - 4-Signal 分数拆解：
    - direct link。
    - source overlap。
    - Adamic-Adar。
    - type affinity。
  - 源追溯。

图谱页不只是可视化，要明确表现 `llm_wiki` 的知识结构：节点、关系、来源、社区和空白洞察。

图洞察能力：

- 惊奇连接：跨社区、跨类型、边缘节点到枢纽节点的意外关联。
- 知识空白：孤立页面、低内聚社区、桥接节点。
- 点击洞察卡片可高亮对应节点和边。
- 洞察可标记为已处理，避免重复打扰。
- 知识空白可一键触发 Deep Research，触发前允许用户编辑研究主题和搜索查询。

### 3.5 检索测试 / 问答召回页签

目标：让用户快速验证知识库是否可用，不做 RAG 评估报表。

输入区：

- 查询文本框。
- 检索按钮。
- 可选模式：
  - 关键词检索。
  - 混合检索。
  - 向量语义搜索。
  - 图谱增强。
- 可选 topK。
- 可选上下文预算，按当前模型能力控制召回内容。

结果区：

- 答案摘要，若启用问答。
- 召回列表：
  - 标题。
  - 命中片段。
  - relative_path。
  - wiki 页面路径。
  - 分数。
  - 来源类型：raw、wiki、image、graph。
- 支持查看原始 JSON，便于调试。
- 显示召回阶段拆解：关键词命中、向量命中、图谱扩展、最终上下文。
- 回答必须带引用编号，并能跳转到对应 wiki/raw/image 结果。
- 支持将高价值回答保存到 `wiki/queries/`，并自动进入摄取流程，提取实体/概念。

多模态图片结果：

- 图片类结果展示缩略图。
- 点击打开灯箱。
- 灯箱中显示视觉 LLM 生成的事实性说明。
- 提供跳转源文件入口。

多会话问答：

- 支持新建、重命名、删除会话。
- 每个会话保留独立消息历史。
- 可配置发送给 LLM 的历史深度。
- 每条回答保存引用来源，刷新后仍可查看。
- 支持重新生成上一轮回答。
- 对支持 reasoning 输出的模型，思考内容默认折叠，生成时可展开查看。

### 3.6 知识导图 / Wiki 结构页签

目标：展示由两步式摄取生成的 wiki 组织结构，而不是普通文件列表。

内容：

- wiki/index。
- overview。
- schema/rules/purpose/log。
- 自动主题分组。
- Louvain 社区映射到的知识簇。
- 每个页面显示来源文件引用数量。
- 点击页面可查看：
  - 页面内容。
  - 引用来源。
  - 最近更新时间。
  - 增量缓存命中状态。

如果页面命名最终采用 `结构` 而不是 `知识导图`，它仍然表达同一个能力：查看 `llm_wiki` 生成出的知识结构。

### 3.7 审核 / Lint 页签

目标：保留 `llm_wiki` 的人工策展能力，让 LLM 维护知识库但不替人做最终判断。

Lint 能力：

- 检查死链、孤立页面、缺失 frontmatter、缺失来源、重复页面、低质量摘要。
- 检查 `index.md`、`log.md`、`overview.md`、`purpose.md`、`schema.md` 是否存在且结构有效。
- 检查 source summary 是否与 raw 文件一致。
- 检查被删除来源是否完成级联清理。

异步审核能力：

- 摄取时 LLM 可生成待审核项。
- 审核项类型固定为预定义动作，不允许 LLM 自造任意动作：
  - 创建页面。
  - 更新页面。
  - 发起 Deep Research。
  - 跳过。
  - 标记已解决。
- 审核项包含来源、建议、理由、预生成搜索查询。
- 用户可批量处理、忽略、重新生成建议。

### 3.8 Deep Research 页签/弹层

目标：从知识空白、审核项或用户输入出发，补充 wiki 里的外部知识。

能力：

- LLM 基于 `overview.md` 和 `purpose.md` 优化研究主题。
- 支持多查询搜索。
- 搜索提供商：Tavily、SerpApi、SearXNG。
- 执行前展示可编辑确认弹层：主题、查询列表、目标 wiki 位置。
- 结果合成为研究页面，进入 `wiki/queries/` 或 `wiki/synthesis/`。
- 研究结果自动进入摄取流程，抽取实体、概念和关系。
- 显示任务进度、日志、失败重试和取消。

### 3.9 Web Clipper / API 能力入口

目标：保留 `llm_wiki` 从网页和外部工具摄取知识的能力，但服务端化实现。

Web Clipper：

- 支持 URL 导入或浏览器扩展投递网页内容。
- 网页内容转为 Markdown 后写入 `raw/`。
- 写入后自动进入同一套两步式摄取流程。
- 前端提供 clipped 页面预览、目标知识库选择和导入状态。

REST API / Agent Skill：

- 服务端提供 Token 鉴权 API，用于健康检查、知识库列表、文件读取、混合搜索、图谱遍历、raw 重扫。
- 后续 MCP Server / Agent Skill 基于同一组 API 实现，不在页面内做桌面 `tiny_http` 兼容。
- 页面可在系统设置中管理 API Token，但第一阶段可只保留接口能力。

### 3.10 设置能力

目标：把原桌面设置改成企业服务端模型池和知识库级配置。

系统/公司级设置：

- LLM 模型池。
- 文本 embedding 模型池。
- 视觉模型池。
- Web Search 提供商。
- 默认语言。
- 默认上下文窗口。

知识库级设置：

- 默认 LLM。
- 默认 embedding 模型。
- 默认视觉模型。
- 上下文预算。
- 是否启用向量搜索。
- 是否启用 raw 自动监听。
- 是否启用 Deep Research。
- 是否启用 Web Clipper/API 投递。

渲染能力：

- Markdown GFM。
- `[[wikilink]]`。
- YAML frontmatter。
- KaTeX 数学公式。
- 代码块。
- 图片、音频、视频预览。

支持格式：

- PDF。
- DOCX。
- PPTX。
- XLSX/XLS/ODS。
- Markdown/Text。
- 图片。
- 音频/视频预览。
- Web clip Markdown。

实现约束：

- 原项目中的 Tauri、Tauri Store、本地 LanceDB、tiny_http、桌面关闭行为、跨平台安装包不作为本阶段实现目标。
- 对应能力必须服务端化：PostgreSQL/pgvector、对象存储、服务端队列、REST API、Web 前端。
- LanceDB 作为原项目能力来源保留在产品语义里；企业服务端实现优先用 pgvector 承载向量检索。

## 4. 不做范围

本阶段明确不做：

- RAG 评估。
- 评估基准。
- 多类型知识库切换。
- Dify、Milvus、LightRAG 类型选择。
- 智能体页面。
- 扩展市场。
- 企业管理后台的完整 RBAC 页面。
- 桌面客户端、Tauri invoke、Tauri Store、本地 tiny_http 兼容。
- 原项目跨平台安装包和桌面窗口行为。

## 5. 验收标准

- LDAP 用户登录后可看到知识库列表。
- 登录后默认进入 `/` 引导页，点击 `开始体验` 进入 `/database`。
- `/database` 展示知识库列表卡片和 `新建知识库` 按钮。
- 点击知识库卡片进入 `/database/{kb_id}`；详情页返回按钮回到 `/database`。
- 所有登录后页面都能通过个人中心退出登录。
- 可创建 `llm_wiki` 知识库，并选择全公司可见或仅创建者可见。
- 创建后数据库记录包含 `tenant_id/company_id`、`created_by`、`visibility` 和真实 `kb_id`。
- 文件落在 `database/{kb_id}/raw/` 下，wiki 页面落在 `database/{kb_id}/wiki/` 下，数据库中只保存相对路径。
- 数据库组合隔离生效：同一路径文件在不同公司、不同知识库、不同 root 下互不影响。
- 文件夹上传保留目录树；源文件记录包含 folder metadata 和 `folder_context`。
- 两步式摄取的分析阶段能看到 `folder_context`，生成的 wiki 页面能追溯到来源目录语义。
- 同路径覆盖上传前必须出现确认对话框，取消时不得覆盖旧文件。
- 公司可见知识库对同公司成员可见，仅创建者可见知识库对其他普通成员不可见。
- 详情页能看到文件目录、raw 目录、wiki 目录、图谱、检索/问答。
- 页面不出现 RAG 评估和评估基准入口。
- 页面文案明确体现 `LLM Wiki`，而不是泛化 RAG 小 demo。
- `wiki/` 中生成并维护 `index.md`、`log.md`、`overview.md`、`purpose.md`、`schema.md`。
- 摄取流程是分析 -> 生成两步，并保留来源追溯、增量缓存和审核项。
- 文件覆盖、删除、重扫都能触发对应的 wiki、图谱、embedding、检索索引更新。
- 图谱展示 4-Signal、Louvain 社区和图洞察。
- 检索结果能展示关键词/向量/图谱召回来源，并能跳转 raw/wiki/image。
- Lint 和异步审核有页面入口，不被 RAG 评估替代。
- Deep Research 能从图洞察或审核项触发，并自动写回 wiki。
